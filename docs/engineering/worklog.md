## 2026-09-01 — feat: one face — Mosvita via the Astro Fonts API, tone replaces the second typeface (01 §3.1/§3.3, brief §3, ADR-014)

- Owner direction: collapse to a single family, let colour and weight carry what the serif carried, keep it bold. Archivo Variable + Instrument Serif regular/italic (56.8KB) → **Mosvita, three static cuts, 34.7KB** — a 22.1KB cut, and less than Archivo cost on its own. Measured 36.7KB → 11.5KB per cut (−69%); the CFF-vs-glyf worry about `.otf` compression did not materialise.
- **Two constraints the family imposed, not preferences.** Mosvita has no Medium, so eyebrows move 500 → 600 (`01 §3.3`) — 500 would have been synthesised silently. And Expanded is a separate drawn master (`usWidthClass` 7), not a `wdth` axis, so each variant carries an explicit `stretch` descriptor; without it `font-stretch: 125%` synthesises a stretch of the 100% cut. `pnpm fonts:inspect` (new, zero-dep sfnt reader) is what established both, plus that all masters cover the retained charset.
- **Astro does not subset and does not convert `.otf` → `.woff2`** — verified against the installed 7.1.1 source, not the docs prose (ADR-014). `subset-fonts.mjs` stays upstream and is still where the bytes come from. What the Fonts API bought: metric-matched fallbacks (`Mosvita fallback: Arial` is in the output), hashed URLs, preload filtering, and the deletion of `public/assets/fonts/` — the same three files had been committed in both trees. **CLS is 0 on every route** despite three files replacing one.
- Deviation from the plan's byte guard: the old 48KB per-file Archivo ceiling only ever ran on a manual `pnpm fonts`, by its own admission. Replaced with a **total** payload cap in `scripts/font-budget.mjs` (50KB) enforced by the asset guard in CI. Headroom is sized to exactly one thing — the reserved `Mosvita-Black` hatch for h3–h5 at 46.3KB — so a fifth cut cannot slip in without amending the doc and the number together.
- Judgment calls: **pull-quotes took the muted rung** rather than the display cut — 900 Expanded for a full sentence read as shouting, and the phosphor rule beside it already does the lifting. **Prices and counts stayed at 400** where they were 400 before; making every readout number expanded was scope creep the swap did not require. **404/500 impact titles gained the display cut** — both were `--text--impact` at inherited body weight in HEAD, a pre-existing gap the "every heading" rule now closes.
- Trap worth recording: the sweep's `class="..."` regex used `\b`, which treats `-` as a word boundary, so it rewrote `footer__legal-sep` → `footer__legal eyebrow-sep` and silently killed the `·` separators. Caught by eye in the footer, then bounded by diffing every class token against HEAD — 0 lost, 0 unexpected across all 25 files. Any future class-injection pass needs `(?![-\w])`, not `\b`.
- Verification: `pnpm verify` clean (147 tests), glyph guard 20 pages, asset guard 41 files, size 70.19/350KB, responsive 17 routes × 4 widths zero overflow, mobile captured at 390 and 320 (`transmissions` — the historical shrink-to-fit word — fits). Lighthouse perf 99, a11y 95–100, LCP 1813–2203ms, CLS 0, TBT ≤6ms.

## 2026-08-31 — fix: the nav wordmark never showed the scent tint (01 §2.4)

- `01 §2.4` says the nav links stay white under a scent-themed section and "the scent shows in the wordmark and an underline marker". The wordmark rule existed and was correct — `fill: var(--scent-tint)` — but **it has never once rendered a scent.** `<Nav />` sits in `BaseLayout` as a *sibling* of the `[data-scent]` scope, not a descendant, so `var(--scent-tint)` inside the nav always resolved to the `:root` fallback: the house accent.
- Invisible until today for the same reason the 404 bug was: volt's tint has always equalled the house accent (UV before, green after), so the one page anyone would eye-check looked right. Halo's violet is the first tint that makes it obvious — a green wordmark over a violet page.
- Fixed by mirroring the scope's `data-scent` onto the nav, so the existing `[data-scent="…"]` rules in `tokens.css` apply to the nav subtree and the tint arrives **through the token system** rather than by copying a computed colour around. `closest()` covers both shapes: the PDP wraps its themed section in `[data-scent]`, the gallery puts both attributes on one element.
- The gallery rewrites that attribute as it scrubs (`gallery.ts` → `showScent`), so a `MutationObserver` on the attribute keeps the nav in step with the active bottle rather than freezing on the first — verified live: the wordmark tracks green → blue → pale through the procession. Observer is disconnected in `destroy()` alongside the triggers (guide §6.2), and the `data-scent` it writes is removed there too.
- Safe to put `data-scent` on the nav: nothing does a global `[data-scent]` query — `gallery.ts` and `pdp.ts` both read `dataset.scent` on an element they already own.

## 2026-08-31 — feat: halo keeps the retired house ultraviolet (01 §2.3 amended)

- Owner call: `halo` carries `#be29ff`, the accent the whole system used until this release. It is the one deliberate exception to the rule that a scent tint tracks its bottle's liquid, and the name is the argument — a halo is the light *around* an object. It also fits the notes better than the green did: iris, orris and heliotrope are all violet materials, and `docs/engineering/worklog.md`'s own copy sign-off flagged iris as load-bearing for this scent.
- **The tint change alone was not shippable, and looking at it is what proved that.** Halo's liquid measures S 0.90 but L 0.92, and at that lightness no hue can carry chroma — beside a vivid violet rim the body rendered as *white*, a mismatched gel rather than the bottle's own glow. Every other scent sits within 16° and ~2 chroma of its own liquid; halo was 178 chroma points away.
- Saturating it does nothing — the saturation is already 0.90. **Deepening is the fix**, so `LIQUID_REHUE` entries became `{ hue, deepen }` and halo is `{ hue: 282, deepen: 0.35 }`: L 0.92 → 0.77, chroma 36 → 103. Chosen over 0.45 (chroma 123) by eye because it keeps halo the lightest coloured bottle of the five, which is what `the glow. iris in soft focus.` asks for. Caps and glass measure chroma 6 and 0 after the pass — untouched, as designed.
- Halo **gains** a tinted text identity it did not have. Under the old palette it was near-neutral pale violet, so `01 §2.4` banned it from text; at `#be29ff` it is 4.47:1, so it takes `--scent-tint-text: #c33afe` (4.84:1) — the same clamp volt used under the old house colour, now free. The §2.4 guardrail was rewritten accordingly: the near-neutral rule now names `static` only, and halo joins phosphor and amber in the display-sizes-only list.
- `static` stays green — it has no equivalent argument, and its pale lilac was the one liquid that genuinely read as a leftover.

## 2026-08-31 — feat: the house goes green (01 §2.1 amended, 00-brief §2)

- Accent moves ultraviolet `#be29ff` → signal green **`#008d57`**, following the replacement `volt` master. Volt is item 01 and its scent tint *is* the house accent, so a green bottle made the violet identity wrong — this is the change the new render forces, not a change of taste.
- **Judgment call on the hex.** The owner proposed `#015833`. It measures **2.21:1** on the page black and cannot carry the focus ring (WCAG 1.4.11 wants 3:1), the `btn-primary` fill or its label, so the hue was kept and the luminance raised to the accent's existing value. `#008d57` is the bottle's own liquid hue (sampled `#008351`, 157°) and is a **luminance twin** of the violet: 4.47:1 on black, 3.42:1 on a light interlude, 4.65:1 for the label — the same numbers, so `01 §2` needed no re-derivation and Lighthouse's posture is unchanged.
- **Neutrals moved by pure OKLCH hue rotation** — L and C preserved exactly, hue set to 157.9°. That is why every measured ratio shifted ≤0.05 and all upward (`ink-3` 2.32→2.36, `ink-4` 3.38→3.46, `haze-3` 8.55→8.71). Amber is untouched: it is the counter-accent and now sits 116° from the house hue, wider separation than it had from violet.

All five now register within 0.001 of canvas fraction.
- **Duotone retuned 42% → 62%, by eye, and it is not a free number.** The mix sets the tint layer's chroma; `#008d57` carries OKLCH C 0.155 where `#be29ff` carried 0.288 (luminance twin, not chroma twin). At 42% the plates read as monochrome-with-a-cast; matching the violet's tint chroma would need ~85%, which posterises. 62% is where the craft grid and both doors read as graded specimen photography again.
- **`02-adrs.md` and `rfc-001` left untouched, deliberately** — a deviation from the plan. Their `#be29ff` sits inside ADR-003, already marked SUPERSEDED by ADR-009; editing it would falsify the record for no benefit. `design-review-2026-08-21.md` is likewise a dated record, so its AI image-prompt block got a superseding banner rather than a rewrite — the prompts brief unproduced assets (AST-03a/05/06/07/08) and would otherwise come back violet.

## 2026-08-28 — feat: mobile as a designed experience (01 §4.2, 03 §7, review OSV-13)

- Closes **OSV-13**. The spec defines four breakpoints; the site shipped one — every media query in the codebase sat at `47.9375rem`, so 768–991px got the desktop layout unchanged. Tablet now takes the 3- and 4-up grids to 2-up (PLP, craft, journal list, social cards); tiny (≤479px) takes social cards to one column. The 2-up grids are deliberately left alone: 400px a side at 834px is the layout working, and `03 §3.1` asks for two columns from 725px up.
- **The mobile site had no navigation.** `.nav__toggle-bar` is an empty span in the markup and nothing ever styled it, so the menu button rendered 12×2px and invisible. The overlay menu behind it worked perfectly; nothing could open it. Collection, the house, journal, contact and the cart were unreachable on a phone. `01 §5.2` specifies the overlay but says nothing about the control that opens it — spec gap flagged, built to the existing register (1px rules, `currentcolor`, 44px box).
- **Horizontal overflow does not scroll on a phone — it shrinks the page.** The browser widens the layout viewport to contain the overflow and scales everything down: `/journal/` laid out at 625px on a 390px iPhone, so every element including body copy rendered at ~62% of its designed size. Invisible in a desktop browser, invisible to Lighthouse. Four independent causes, each found by measurement: the footer marquee never had `overflow: hidden` (the campaign one always did); `.article__xsell` used negative-gutter margins to break out full-bleed but is a *sibling* of `.article`, so it overhung by a gutter each side at every width (1440 + 2×57.6 = 1555px); `.contact` used `1fr` tracks, which are `minmax(auto, 1fr)` and refuse to shrink below min-content (350px column in a 320px viewport); and `business@osvant.com` is one unbreakable 19-character token at `--text--h3`.
- **`01 §3.2` amended with owner sign-off — the clamp floors.** `--text--impact` `clamp(4.5rem, 12vw, 8rem)` → `clamp(2rem, 10vw, 8rem)`, `--text--h1` floor `3rem` → `2rem`. A 4.5rem floor means "never smaller than 72px", and one long word at 72px cannot fit a 320px screen — that overflow was the root cause of the two routes the other fixes could not reach. Desktop is untouched: at ≥1280px both old and new middle terms hit the 8rem cap, so impact still computes to 128px. Visible only between ~768–1280px, ~17% smaller (1024px: 123 → 102px). The *extreme jump* `01 §3.2`'s own note protects is preserved — impact is still 2.8× h1 at the cap.
- **Touch targets**: nav and footer links were 17px tall boxes, under half the 24×24 WCAG 2.5.8 minimum. 13–24 undersized targets per route → **0**. Gated on `pointer: coarse` rather than a width breakpoint, because the constraint is the finger and not the viewport; verified on iPad gen 7, iPad Pro 11 and Galaxy Tab S4. Every rule grows the hit area, never the type. Inline prose links deliberately excluded — 2.5.8 exempts them.
- **`scripts/check-responsive.mjs` is the new merge gate**: 17 routes × 4 breakpoints, fails on horizontal overflow only. Column counts and tap sizes are design judgement with legitimate exceptions, and a gate that fires on judgement calls gets disabled; overflow has none. It skips clipped ancestors when naming the culprit — the footer marquee is 4000px wide by design and would otherwise be blamed on every failure. Verified by deliberate violation.
- **Method note, because it cost time.** The first audit reported phantom overflow on four routes: it compared `scrollWidth` against the *requested* device width while the page was actually laying out at 625px, which was itself the bug it was trying to find. Measuring against real `innerWidth` and surfacing shrink-to-fit as its own finding is what made the causes legible. Chrome extension automation also silently blocked three iframe-based attempts; Playwright was the right tool and is now the guard's foundation.
- **Making the toggle pressable exposed two more pre-existing bugs, both invisible until then.** (1) `backdrop-filter` creates a containing block for `position: fixed` *descendants*, so with `nav--solid` applied the overlay's `inset: 0` resolved against the nav's own 84px box rather than the viewport — the menu painted as a strip across the top with its links spilling over the page behind it. The blur is dropped while the menu is open; the overlay covers everything, so there is no backdrop left to blur. (2) `01 §5.2` asks for menu links at `--text--h2`; that was set on the list, but `.nav__links a` sets `--text--btn` and a rule on the anchor outranks an inherited value, so the overlay shipped at 16px against a spec asking for 40px.
- **One self-inflicted regression worth recording.** The first touch-target rule used `display: inline-flex` to centre link text in a 44px box, and `the house` started rendering as `thehouse`: SplitText wraps each word in an inline-block div, and a flex container *removes* the whitespace between items rather than collapsing it. Same visible symptom as OSV-03, different mechanism — that was a missing `{" "}` in JSX, this is CSS deleting a space that is still present in the DOM, so `a.textContent` reads `"the house"` either way and markup review cannot catch it. Fixed by padding to the target instead of switching `display`.
- `pnpm verify` green (146 tests, 0 errors/0 warnings); copy, glyph, asset and responsive guards clean; bundle 69.89KB/350KB. Lighthouse unmoved or better: `/` 2136ms, `/collection/fever/` 2161ms, `/the-house/` 1975ms, perf 98–99, a11y/best-practices/SEO 100.

## 2026-08-27 — perf: font subsetting closes the LCP miss (06 §1, 01 §3.1 amended, OSV-31)

- Implements `06 §1` ("Archivo Variable woff2 **(subset latin)**") and `06 §4` ("font subsetting → engineering"), specified since the first font commit and never done. Archivo shipped as the full 88KB Google delivery — the largest single resource on every page. `pnpm fonts` (`scripts/subset-fonts.mjs`) now emits subsets: **118KB → 56.3KB**, Archivo alone 88.0 → 35.8KB.
- **Result: every page clears the 2.5s LCP budget.** `/` 2630 → **2143ms**, `/collection/fever/` 2629 → **2068ms**, `/the-house/` 2400 → **1977ms**; perf 97/97/98 → **99** across the board, a11y/best-practices/SEO 100. Full 20-page LHCI sweep green against the repo's own assertions.
- **Two reductions, and the second is the one worth remembering.** Charset alone only bought 39% (88.0 → 53.5KB), because a variable font's weight is variation deltas per glyph rather than glyph count. The `wdth` axis is the expensive one — dropping its unused 62–100 range saved another 16.6KB, more than removing ~150 glyphs did.
- **`01 §3.1` amended with owner sign-off**: axes narrowed from `wdth` 62–125 / `wght` 100–900 to `wdth` 100–125 / `wght` 400–900. Nothing in the built site rendered outside the narrow range; the two apparent uses of the extremes were the `@font-face` descriptor lines, not usages. Zero rendered pixels change. The `@font-face` descriptors were narrowed to match the file, because a range declared in CSS that the woff2 does not carry fails silently — the browser synthesises it, so `font-weight: 100` would render a faked thin rather than Archivo Thin.
- **`check-glyphs.mjs` is the price of subsetting** and ships with it, not after it. A character outside the retained set renders as tofu, and would only surface when someone wrote a journal article containing an umlaut. It reads built output, shares one charset module with the subsetter so the two cannot drift, and names both fixes in its failure message. Verified by deliberate violation — three planted characters, each reported with its codepoint. Wired into `ci.yml` beside the copy guard.
- **Corrects the previous entry's diagnosis, which was wrong twice.** The bisect that settled it: removing the font moved LCP 2630 → 1986ms, removing all module JS moved it → 2180ms, and deferring script execution to `window.load` moved it **0ms** — which ruled out main-thread contention and pointed at the font. The photography was never implicated; observed LCP is 86ms on real hardware and the whole number is Lantern simulation (150ms RTT, 1.6Mbps, 4× CPU).
- **`subset-font` added as a build-only devDependency** (harfbuzz). Same class as `sharp`: ships nothing to the client, so no ADR under the runtime-dependency rule — flagged because it is a native binary. Font sources moved to `src/assets/fonts/` (never served); generated subsets live in `public/assets/fonts/`, which needs stable unhashed URLs for the preload. Both committed so a fresh clone builds correctly without running the script first.
- A 48KB ceiling on the Archivo subset is asserted inside `subset-fonts.mjs`: if a source drop or a `subset-font` upgrade ever stops shrinking it, the budget miss returns quietly and nothing else in CI watches that number.
